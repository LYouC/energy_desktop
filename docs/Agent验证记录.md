模型为 `deepseek-ai/DeepSeek-V4.1-Flash`，通过 SiliconFlow 的 OpenAI 兼容接口调用。最新复验结果生成于北京时间 2026年11月16日 22时29分18秒，六条真实模型用例的程序断言均通过。独立语义评审确认本轮六条样例的核心操作、授权边界和推进建议基本符合场景要求。容量冲突的时间分配已修正，背景中的时间与事实标记、工作日表述和部分协助措辞仍有细节问题。下文保留22时20分与22时24分轮次的发现和修复过程。

本轮脚本 `tests/agent.live.ts` 调用真实生成函数，再通过 `applyAgentTurn` 验证内存中的业务结果。它覆盖模型调用、有限工具提交和业务应用。数据库事务、Electron IPC、界面交互及重启恢复的结论需结合各自测试记录。

## 发现的问题及修复前后

### 记录行为与文字声称

中间轮次的 S01 回复声称“我先把这个任务记下来”，同时说卡片会保留待确认，实际返回 `actions: []`，程序检查发现任务数为零。运行层随后补充明确记录意图与拆分建议的完整性校验，工具错误反馈回同一循环，要求提交相应业务动作。当前结果包含一个创建动作和两项待接受建议，程序检查通过。

这些完整性检查采用有限表达匹配。不同表达、否定和混合意图仍需扩展场景验证。

### 相对日期解释

中间轮次把2026年11月16日的“下周五”解释为11月20日。运行层补入由程序计算的今日、明日、本周五和下周五日期锚点，提示词要求按锚点解释日期。当前 S01 使用11月27日，S08 使用11月17日，两项日期正确。跨月、跨年及用户指定时区等情况仍待验证。

### 混合语句中的授权证据

22时20分轮次的 S01 创建与接受用例先遇到授权引用校验失败。模型按工具反馈，把创建或接受的明确短句与“建议”“今天先不安排”等其他分句分开引用，同轮修正后提交成功。该轮 `trace.validationErrors` 记录了修正过程。22时24分的六条用例均在一个模型步骤提交。22时29分最新轮次的 S01 创建和 S03 使用两个模型步骤，其余使用一个步骤，六项校验错误数组均为空。

校验修正会增加模型步骤和请求开销，尚需观察多轮情况下的稳定性与调用量。

### 建议正文缺失

22时20分轮次的 S03 仅指出超量，并以“建议如下”结束。补充纯分析回复完整性和事实强度提示后，22时24分复验给出了主线任务、最小版本、协商范围和关键追问。正文缺失得到修复，该轮具体规划仍有以下错误。

- 用户估计演示需2小时，可用3小时。回复称“报告和演示各自都留不下完整版本”，超出了现有估时能支持的结论。
- 主线分配约2小时，另一件分配0.5–1小时，此后“剩下约1小时”的说法无法成立。求助和协商也需要计入三小时总量。
- 回复提出“今晚20点前”联系对接人和“今晚21:30”切换任务。复验发生在北京时间22时24分，这些时刻已经过去。建议应优先使用相对时长，给具体时刻前核对当前时间和实际截止。

随后新增 `shared/capacity.ts` 和 `calculateCapacity` 工具，由程序核算估时总量、缺口、单项是否能装下，以及包含缓冲的条件性分配。22时29分复验采用演示120分钟、报告部分45分钟和缓冲15分钟，合计180分钟。回复明确报告完整版本需要协商，已修正前轮的时间分配和过去时刻问题。

该工具提供算术结果和条件性候选，任务价值、实际交付标准和用户是否接受仍由协商决定。程序检查继续结合语义评审核对纯建议的可执行性。

### 事实和原因的表达精度

- S01 前轮把“材料有了”扩写为“材料齐了”“材料已收集整理”。最新轮次使用“材料已有，尚无提纲”，已修正事实强度。
- S04 前轮将“成本中心”概括为“花钱、但不直接赚钱的部门”，把利润中心解释成“挣钱的那些”。后续两轮继续用部门例子与费用归集帮助理解，面试表述仍较简化。最新轮次开头“这个词本身不难”也可能让用户觉得阻力被轻视，宜直接解释概念。
- S06 前轮给出未经证实的休息方式原因定论。最新轮次承认疲惫，围绕已发现的错因给具体动作，原因表达已修正。进一步改善可把强制停止式措辞改成协商检查点。
- 最新 S01 正文新增“剩下6个工作日写正文也不算紧张”。按11月16日至11月27日的普通周一至周五推算，6个工作日缺少依据，用户未来的可用时间也尚未知，充裕程度应保留不确定性。
- 最新 S01 背景把“用户今日14:28提出”写入用户事实，实际运行本地时间约22时28分，14时28分来自 UTC 时间。时间需要按用户时区呈现。背景同时写入“提纲未定，正文无法稳定开始”，这是 Agent 的判断，应与用户明确说出的事实区分。

## 连续七轮流程复验

结果文件 `test-results/agent-journey.json` 生成于北京时间2026年11月16日22时57分06秒。测试使用同一会话依次运行 S01 的澄清、记录、接受、受阻协助、缩小范围、阶段结束与停点承接，七轮程序断言均通过。第七轮先对工作区进行 JSON 序列化重读，再在同日继续交流。

该次复验发生在新增连续协商约束和授权范围校验之后。前述六条样例保留22时29分的运行结果，两批结果对应不同阶段的提示词和校验版本，六样例尚未在最后一版约束下全部重跑。

| --- | --- |
| 第一轮模糊想法 | 通过。询问已有材料与截止，动作为空，未创建任务或承诺今日安排。 |
| 第二轮记录与建议 | 核心通过。一个父任务保存，拆分和今日范围进入待接受方案。周五解释为11月20日，背景保留“下午交”，正式安排为空。回复提到的未来缓冲尚缺可用时间依据。 |
| 第三轮接受拆分与提纲安排 | 核心通过。`resolve` 仅接受拆分条目，另一个直接 `schedule` 依据“今天只安排整理提纲”建立唯一今日范围。旧日程建议仍为 pending，正文和其他步骤没有正式排期。接受证据与条目范围一致。 |
| 第四轮卡住协助 | 具体入口有效，表述有缺口。给出组织框架、分节标题和材料归类的方法，动作为空，实际安排保持已接受范围。文字却说“今天这一小时的目标就降到”新范围，容易让用户误以为正式安排已更改，宜明确其为待协商建议。 |

| 第七轮继续 | 承接核心通过。使用三个问题和未完成提纲建议下一步，动作为空，保留已完成的今日阶段。没有编造三个问题的实际内容。根据先前推断认定当天一小时已经耗尽，并把建议偏向明天，承接时应重新核实剩余时间。 |

### 连续流程发现与修复

首轮尝试保存在 `test-results/agent-journey.initial.json`。第三轮明确说“就按你这份拆分建子任务”时，授权表达误被拦截，导致该轮无法应用。第五轮把“这个可以”扩大成接受旧方案，同时把用户明确要求的三个问题范围作为新提案，已接受安排仍保留旧范围。开发随后补充相应授权表达、同条消息具体范围的优先级，以及回归检查。

后续审阅还发现第三轮的引用只指向拆分，却接受了同方案的日程条目。最终增加条目范围校验。22时57分结果只用拆分引用接受拆分，日程由单独的明确安排指令执行，旧日程建议仍待接受。第三轮经过同一模型循环中的校验反馈后完成，测试额外核对旧日程条目没有被误接受。

### 连续流程保留的质量问题

- 第四轮把卡点直接判断为“材料本身不卡你，卡的是组织”，表达比用户已确认的信息更强。具体框架可以作为试用建议，原因应保留可核实性。
- 第四轮文字声称降低今日目标，动作却为空。正式数据守住了授权边界，但对话对生效状态的解释仍可能误导。
- 第五轮用户只明确改为“三个讨论问题”，动作又指定成果、问题、下一步三种问题类型，并写“接下来的一小时”。这些细节来自 Agent。此前用户已经花了二十分钟，剩余时间需要重新核实。
- 第六轮背景进一步把上述三类问题写为已完成的用户事实，还断言“今天已用掉可用的一小时”和所有报告步骤均未开始。用户只确认三个问题列出和完整提纲未做。第七轮受该记忆影响，直接判断今天时间已耗尽，展示了背景过度提炼如何影响后续建议。
- 第七轮能从已知停点继续，提供两种方法，但“周五下午交，时间还够”和“选 A 最稳妥”缺少未来容量依据。建议应与新可用时间条件协商。

这些问题没有改变父任务目标、真实截止或整体完成状态，仍属于后续需修正的事实质量与对话一致性问题。

## 覆盖范围与后续验证

六条样例加连续七轮流程覆盖十二组场景中的部分路径。S01 第一至六轮已连续执行，第七轮已验证同日序列化重读后继续，跨日与真实桌面重启后的完整会话仍待验证。独立桌面用例验证了一条真实创建任务和重启恢复路径。事实纠正、能力不足后换路径或讨论放弃、临时会议后的连续拒绝、含糊指代、跨任务部分接受、能量请求边界、父子任务完成条件，以及旧方案和故障的全部分支也需要继续验证。

最新轮次的每个样例各执行一次。此前轮次中多个样例经历工具循环内修正，程序通过与语义质量应分别保留结论。稳定性需要同场景多次运行、表达变体和连续会话，并结合真实用户是否能开始行动的反馈判断。
